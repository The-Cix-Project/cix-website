Operator model

What survives a host upgrade?

On a same-kernel roll, Cix can replace its running control plane while workload processes keep their IDs. A workload image update has a different lifecycle. Its container can restart, and state that must survive belongs on a volume.

Control-plane updates

What changes during the handover?

When the staged root carries the running kernel, the host roll waits for quiescence, hands cixd’s runtime state to its successor, switches the root in place, and confirms the new slot. Containers continue running. Host console shells respawn from the new root. Open API streams and container-console connections drop and clients must reconnect.

A kernel change still reboots. If the switch is refused or fails before the root changes, the roll reboots into the staged slot. A failure to start after the root changes reboots into the previous slot. See the measured API interruption.

The lifecycle

From deployment to readiness.

Deployments name the image, placement, network, storage, files, services, and restart policy a workload needs. If the image is not ready, Cix queues the work and reports that it is awaiting the image rather than making the operator perform a manual round trip.

Deployment and delivery

Reapply intent with retained credentials.

Deployment applies retain supplied secrets in a private state file and reuse them on later applies. Existing containers can be updated or restarted through the rolling mechanism; changes to creation-only fields still require removal and reapplication. Secrets are included in system backups and are not returned by inspection reads.

Roll groups restart one member at a time. Installs blocked by shared work or occupied build slots can enter a persistent queue, returning a position and reason. Duplicate queued requests and other invalid requests can still be refused.

Management addressing, recorded uplinks and saved routes are restored after reboot. Confirmed boot slots now outrank older entries even after a clock correction.

03

State and updates

Keep durable state where it belongs.

A container root is derived from its image. Image policy controls whether recipe changes are followed, whether applying a recipe converges installed packages, and whether a backward pin is allowed. Writes made inside that root do not survive a new derived root. Persistent data belongs on volumes, where size limits and usage are explicit.

04

Image policy

Choose when images follow recipes.

An image recipe, its live manifest, and its installed packages are three useful views of the same intent. Set the policy explicitly: follow or manually apply recipes, declare or converge installs, and refuse or allow downgrades. Export the live manifest when the box is the source of a recipe.

Rolling dependencies

Keep runtime dependencies moving too.

In an image with at least one rolling entry, runtime dependencies that are not explicit manifest entries follow the newest published versions through the normal install and ABI checks. Versioned dependency requirements stay held, and images whose entries are all pinned retain their dependencies. Following containers can restart as their images converge.

Visible boundaries

Who can approve a change?

Check the acting identity, the configured approval gates and the storage a deployment can modify.

  • Permission-aware accessOnce host authentication is active, protected reads and operations require the permission declared by the API. A 401 means log in; a 403 means the session is valid but its groups do not grant the required permission. App passwords support scripts and automation, but cannot write identities or mint credentials.
  • Approval gatesPublish, rolling, and host-deploy gates default to off. When enabled, the affected item is held and reported as blocked until approval is granted. Provider ABI changes are visible as a compatibility boundary rather than silently rolled through consumers.
  • State placementContainer roots are image-derived; durable state belongs on volumes and explicitly placed storage. Disk role assignment and destructive formatting are separate actions, and the OS disk is protected from both.
  • Namespace containersCix workloads use Linux namespaces and cgroups. Direct device grants are not a hypervisor or VFIO/IOMMU isolation boundary.
  • Hardware confidenceSome real GPU, physical-NIC, and wireless paths have narrower verification than software-only and emulated paths.
