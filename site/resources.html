Resource model

Give a workload a disk, a port or a radio.

A container can use real hardware. The operator chooses the device and the storage that outlives the container. For existing data, Cix can mount a filesystem by UUID and leave its contents in place.

Existing data and firmware

Bring the filesystem you already have.

A volume can adopt an existing disk filesystem by UUID without moving its contents. Cix refuses ownership changes, quotas, snapshots, restore, migration and formatting for adopted data; deleting the volume forgets its record. An absent filesystem does not fall back to an empty directory.

On 19 November a USB radio’s driver declared a missing firmware file. Cix found the package output and installed it in the host firmware image. After an operator reloaded the driver, the kernel reported firmware 30.20.0 and the access-point container brought the radio up. Client association remained untested in that run. Containers

Each workload gets namespaces, a cgroup, an image-derived root, network attachments, resource limits, declared services, and optional hardware.

Networks

Bridges, veth, routes, VLANs, addresses, physical interfaces, and whole wireless radios are configured through the custom C data plane.

Storage

Disks and partitions are enumerated live, assigned explicit roles, and can be formatted through a separate destructive action. Filesystem identity and capacity are probed in a helper snapshot, so the API can say “probing” instead of blocking the daemon or guessing that a disk is empty.

What an operator controls

Which state survives replacement?

Cix exposes the mechanisms that decide where work runs and what it can touch. The API records intent; the daemon applies it to Linux primitives and reports the result.

01 / Isolation

Namespace containers, with an explicit root boundary.

Workloads use Linux namespaces, cgroup v2 controls, and user namespaces by default. Their image-derived roots are presented through id-mapped mounts; trusted internal build containers may opt out where required. Capability bounding-set trimming still applies. This is a container boundary, not a VM or a complete hypervisor isolation boundary.

  • Linux namespaces, user namespaces, and cgroup v2
  • Id-mapped image-derived roots
  • Capability bounding-set controls
02 / Persistence

Put durable state on volumes.

Volumes outlive containers and can carry an enforced size limit. Usage is measured through the kernel’s quota accounting where available, with the accounting source exposed rather than hidden.

  • Persistent data
  • Size limits
  • Live usage and backups
03 / Hardware

Grant hardware by intent.

Operator-named mappings can follow matching hardware when it moves. Device access is explicit, shared ownership is checked, and attach/revoke is reflected through the API.

  • PCI, USB, GPU, radio
  • Physical network interfaces
  • cgroup device filtering

Hardware boundaries

Which hardware paths were exercised?

Evaluate the exact machine against the source guide. Cix keeps narrower verification visible rather than turning a capability into a compatibility promise.

  • Namespace containersContainers are not virtual machines. Direct device grants do not provide VFIO/IOMMU hypervisor isolation.
  • WirelessA real 2.4 GHz access point runs with its radio in a container, but client association, over-air DHCP, and end-to-end wireless-to-wired traffic remain narrower proof paths.
  • GPU and physical NICsDiscovery, grants, and API paths exist, while some positive real-hardware scenarios have less verification than software-only or emulated paths.
  • Storage compatibilityThe installer documents covered paths and exclusions. Check the current installation guide before choosing disks, controllers, or a hypervisor configuration.
