Engineer’s entry point

REST and MCP share a permission check.

Cix serves both interfaces in its host daemon. An MCP call runs the underlying API handler with the caller’s directory permissions. The CLI and dashboard use REST to reach those same resources.

Native access for AI agents

MCP runs inside the control plane.

Compare two agents’ DNS permissions →

Cixd serves eligible API operations as typed tools through POST /v1/mcp. Calls use the REST handlers, permissions, and audit path. Long-running operations can park and resume, and non-JSON files return as typed base64 resources.

Each agent uses a directory identity and revocable app password. Group membership supplies role-based access control (RBAC): tool discovery is filtered by permissions, and execution checks them again. The standard agent group grants reads and gateway access; writes require additional grants. MCP is disabled until an operator enables it.

Permissions apply to an area and verb. For example, services:write permits changes to both DNS records and DNS servers; a DNS-record-only role is not currently expressible. App passwords never satisfy identity:write, even for an administrator’s identity. The app password authenticates the request; directory membership determines its permissions.

01

Read first

Authenticate before reading protected state.

Cix keeps liveness public, but host state is protected once authentication is active. health, login, logout, and whoami remain available without a session; reads such as boot, containers, networks, storage, services, packages, and logs require the permission named by the API contract.

02

Change safely

Write intent, then read the effect back.

Mutations are ordinary REST requests: create or update a resource, then read the resulting state and its derived readiness. The CLI and dashboard do not have privileged side channels, so an integration can use the same evidence as the first-party clients.

curl -s http://cix-host/v1/health → {"status":"ok","auth_gating_active":false}

Authorisation

Permissions follow the contract.

Every operation declares one permission in OpenAPI. A session or app password receives the union of its groups; missing credentials return 401, while a valid identity without the required permission returns 403. App passwords are for automation and are sent as HTTP Basic credentials on each request.

Integration boundaries

What a credential can reach.

Check the permission on the operation, the grants on the caller’s groups and any restrictions on the credential itself.

  • OpenAPI is authoritativeUse the versioned OpenAPI contract for exact schemas, status codes, and route names.
  • cixd owns side effectsClients express intent; the daemon validates, persists, reconciles, and drives Linux primitives.
  • Roles constrain automationUsers receive the union of their groups’ area-and-verb permissions. An app password can automate REST and MCP, but never writes identities or creates credentials.
  • Managed LDAP listeners are explicitLDAP server listener selection and ports are API-owned. A client’s TLS choice points to an enabled server listener, while a requested server restart is sequenced one provider at a time.
  • Containers are not VMsWorkloads use namespaces and cgroups. Device grants do not create a hypervisor isolation boundary.
  • Authentication is not optional once enabledPlan for a session token, admin-group bootstrap, refusal auditing, and physical or hypervisor recovery if credentials are lost.
