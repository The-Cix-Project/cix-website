Choose an evaluation path

Start where the risk is lowest.

Cix is beta software. Keep the first evaluation disposable, preserve console access, and read the current installation boundaries before writing a real disk.

01 / Virtual machine

Inspect the API in action.

For Proxmox, use a UEFI OVMF machine with Q35. Use the current signed x86-64 installer, a supported virtual disk path, and a management interface you can reach from your client.

Verify the installer →
02 / Dedicated hardware

Evaluate the machine.

Use a machine with UEFI, console access, documented storage, and a management interface. The installer writes the target disk; treat the installation as destructive to existing data.

Review installation boundaries →
03 / First useful result

Reach the API.

After installation, confirm health from a client, inspect boot identity, and create the first image, network, and container through the same API used by the CLI and dashboard.

Run the quickstart →
04 / Decide

Measure fit honestly.

Check the workload, hardware, storage, and recovery boundaries that matter to you. Cix does not claim VM isolation, broad hardware certification, or production readiness yet.

Review current boundaries →

Before you commit

Know what the trial proves.

A successful boot proves that this image runs on this target. It does not prove every device, workload, or production requirement.

  • Installer trustDownload the ISO, detached signature, and release key; verify the signature on a machine you already trust before writing the image.
  • Container boundaryWorkloads use Linux namespaces and cgroups. Cix containers are not virtual machines, and direct device grants are not a hypervisor isolation boundary.
  • Beta boundaryExpect narrower hardware proof and changes between releases. Keep console access and backups available while evaluating.
  • Next stepOnce the API and first workload make sense, use Operate, Resources, API, and Build for the depth that matches your work.
