The case for Cix

Why run Cix?

Cix runs container workloads on a dedicated host. Choose it when you want to manage applications, disks, network interfaces and infrastructure services through one host API.

The premise

Linux already has the primitives.

Namespaces isolate processes. Cgroups govern resources. Btrfs snapshots provide cheap image-derived roots. Rtnetlink configures the network. Device nodes connect workloads to hardware. Cix builds a coherent operating system around those mechanisms instead of replacing their semantics with an opaque control layer.

01

Change the host under running workloads.

Cix stages a new read-only root in the inactive slot. On a same-kernel upgrade, the new daemon can take over the existing containers. Kernel changes use a reboot.

Inspect the host architecture →
02

Build the system on itself.

Cix’s package system connects recipes, verified inputs, builds, packages, immutable images, artefacts, and rolling delivery. It can use its own container and recipe machinery to rebuild Cix and the kernel on-box.

Read the build guide ↗
03

Give an agent a separate identity.

cixd alone reaches the runtime and host primitives. Its native MCP gateway checks each tool call against the same permissions as REST. Agents use revocable app passwords. The daemon refuses identity writes with those credentials, even for a user whose groups grant them.

Inspect the MCP access model →
04

Hardware is explicit.

A workload can receive a physical interface or a device grant. A volume can adopt an existing filesystem by UUID, keeping its contents in place.

Inspect storage and device grants →

Deployment fit

Start with one dedicated machine.

HostEvaluate the alpha on an x86-64 UEFI machine or in a VM. Check storage and device support for the workload you intend to run.

IsolationWorkloads share the host kernel. A device grant gives a container direct access to that hardware.

ScopeCix manages the local host. Multi-host scheduling remains outside the current operating model.
