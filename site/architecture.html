System architecture

How a request reaches the kernel.

An agent requests a tool over MCP. An operator uses the CLI or dashboard. Both reach cixd, the host daemon that checks the caller’s permissions and applies the operation to the running machine.

01

Client surfaces

Two interfaces reach the same handlers.

cixctl, the dashboard, the physical console, and external automation all use the same API contract and permission checks. For an MCP call, cixd checks gateway access and the permission on the requested operation before invoking its handler. Inspect the permission model.

02

Control plane

cixd is the authority.

A single-threaded, non-blocking epoll reactor written in C and compiled with TCC. It is the only process linked directly to the container runtime and the only process with direct runtime, network, DNS, PKI, LDAP, and package access.

03

Runtime mechanisms

How the daemon isolates workloads.

Namespaces + cgroupsclone3(), PID namespaces, mount namespaces, cgroup v2, and pidfds.

Btrfs snapshotsEvery container root is a snapshot of its image version; the image store is btrfs and required.

Rtnetlink + nl80211Custom C networking speaks directly to the kernel for wired links, routes, and whole wireless radios—no OVS and no eBPF data plane.

Device grantsReal device nodes, shared-ownership checks, and cgroup device filters expose explicitly assigned hardware.

04

Workloads

Containers carry supervised services.

Each deployment names an image and receives its own namespaces, cgroup, filesystem diff, network attachments, limits, configuration, and optional hardware. If its image is not ready, the deployment waits while the shared pipeline converges it. Container-visible /proc reports limits and usage. A container declares services[]; freestanding cix-init supervises them, while the API exposes derived readiness and per-service lifecycle actions.

05

Host OS

Write, verify, cut over.

Cix boots a kernel.org Linux kernel with cixd as PID 1 and no initramfs. Operators choose a pinned, longterm, stable, or mainline tracking policy through the API. The control-plane root is read-only squashfs. Host updates stage and verify a new root in the inactive slot. With the same kernel the daemon can switch roots in place. Kernel changes reboot through the EFI boot manager, which counts boot attempts for rollback. The EFI boot manager is built by Cix’s TCC Win64 cross-target alongside the native compiler. A running Cix host can also build the control plane, kernel, root filesystem, and installer through its source-build system.
